# ブレッドボード段階的ブリングアップ手順

ブレッドボードでサブシステムごとに切り分け検証し、最後にユニバーサル基盤へ移設する。
各 Stage は**前段が緑になってから**進むこと。**プロペラは終始外す**。

前提機材（本セッションで確定）:
- 給電: **安定化電源(PSU)**。電流制限を効かせ、Buck誤設定によるPico破壊を回避。LiPo+BuckはStage Fで導入。
- CRSF切り分け: **オシロスコープ**（GP0波形・反転極性・ボーレートを直接確認）。
- ゲームパッド: **汎用HIDパッド**（決め打ちパーサ。Stage Cで実機バイト配置を確認・調整見込み）。

詳細な単票チェックは `hardware-validation.md` を参照。本書はそれを段階順に割り当てたもの。

---

## Stage A — 電源のみ（過電圧でPico即死を防ぐ）

目的: Picoに正しい5.0Vだけが入ることを、Pico接続前に確定する。

1. [x] PSU出力を **5.0V / 電流制限 ~0.7A** に設定し、**テスターで実測**。
2. [—] （Buckを使う場合のみ）Buck OUT+ を**テスターで実測5.0V**に調整。可変品は初期12V等がある。→ 今回はPSU直、Buckは Stage F で導入。
3. [x] 極性確認: OUT+ → Pico **VBUS(pin40)**、OUT− → Pico **GND(pin3)**。**VSYSではない**。
4. [x] Pico単体を接続（ゲームパッド・TX・LED未接続）。PSU電流が数十mA程度で安定（突入後）。
5. [x] 内蔵LEDが点灯 or 点滅（ファーム次第。未書込なら消灯でOK）。異常発熱が無いこと。

> ✅ 合格条件: VBUSに5.0V±0.1、過大電流/発熱なし。

**実施記録 (2026-07-16): 合格。** VBUS実測≒5.0V、消費電流 0.02A(20mA) で安定、発熱なし。

## Stage B — モードUI（ファーム＋UART＋LED＋ボタン、無線なし）

目的: ファームのUIロジックと GP2/GP10-12 配線を、ゲームパッド・TXなしで検証。

配線追加: GP4→USB-シリアル変換RXD（GND共通）、GP2→タクトSW→GND、GP10/11/12→LED→330Ω→GND。

1. [x] 書込: ゲームパッド・外部5Vを外し、BOOTSEL押しながらmicro-USB接続 → `./scripts/flash.sh` → 配線復帰。
2. [x] `./scripts/monitor.sh`（921600bps）で起動バナー・`Mode: SIMPLE`・`signal inversion: ON` を確認。
   → **⚠️ 手元のFTDI変換器では `./scripts/monitor.sh 115200` を指定しないと化ける**（下記「既知の問題」）。
3. [x] `?` でコマンド一覧が返る。
4. [x] 起動直後 **青LED(GP12=SIMPLE)** 点灯。
5. [x] 短押しごとに `# mode -> RECORD/PLAYBACK/SIMPLE`、LEDが **赤→緑→青** と移る。
6. [x] PLAYBACK中に**長押し(0.6s)**で `# playback START/STOP`（データ無しでもトグルログが出る）。

> ✅ 合格条件: 3モード循環・LED対応・短長押し判定が全て一致。

**実施記録 (2026-07-16): 合格。**
- モード循環・長押し判定ともログで確認、LED3個の点灯もモード名と一致することを目視確認済み（1ピンずれ修正後）。おまけに記録→再生フローが一巡した:
  `# mode -> RECORD` → `# recording started` → `# mode -> PLAYBACK` → `# recording stopped, flushed 137 samples to flash`
  → `# playback ready: 137 samples` → 長押しで `# playback START (137 samples)` → `# playback finished`
- 137サンプル ÷ 50Hz = 2.74秒 で、ログのハートビート(1秒毎)間隔と一致。**再生レートが設計どおり**であることを確認。

### ハマった点（次回の切り分け用）
- **タクトSWの向き**: 4本足の同じ側2本は内部で短絡済み。90°回して挿すとGP2がGND常時短絡＝無反応になる。**対角の2本**を使う。
- **ピンの数え間違い**: LED3本を pin14/15/16 のつもりで pin13/14/15 に挿し、1本目がGND(pin13)で点灯せず。手元のPicoは **pin20(GP15)にヘッダが無い**ため下から数えるとずれる。**GND(pin3/8/13/18/…、5ピンおき)を基準に数えること**。

### 既知の問題（未解決）
**デバッグUARTのボーレートが8倍ずれて見える。** 手元のFTDI変換器(`/dev/cu.usbserial-A5069RR4`)では `monitor.sh 115200` でのみ正しく読める。
- ファーム側は正常と確認済み: 逆アセンブル上 `stdio_uart_init` は `uart_init(uart1, 0xE1000=921600)` を呼び、GP4/GP5 も正しい。ソースに `set_sys_clock` 等のクロック変更は無い。
- よって**変換器の分周器バグ（FT232R偽物チップ）が犯人という仮説が有力**だが未確定。
- **Stage Dでオシロを出すときに GP4 のビット幅を測って決着させること**: **1.09µs なら921600**（＝変換器が犯人・実害なし、monitor.shに115200を渡し続ければよい）、**8.68µs なら115200**（＝ファーム側の問題。25Hzストリームの1行が1.4ms→11msに膨張し500Hz送信を破壊するため、Stage C/Dの前に要修正）。

## Stage C — ゲームパッド（USB Host / HIDパーサ確定）

目的: 汎用パッドの生HIDレポートから軸/ボタンのバイト配置を確定し、必要ならパーサ調整。TXはまだ繋がない。

配線追加: ゲームパッド ─OTG(micro-B→A)→ Pico micro-USBポート。（書込用ポートと共用のため、以降の書込は都度パッドを外す）

1. [ ] SIMPLEモードでパッドを操作しつつ `d`（スナップショット）。
2. [ ] `(1) HID raw` が全0でない。**VID/PID を控える**。
3. [ ] 各スティック/ボタンを個別に動かし、`(1)`のどのバイトが変化するか対応表を作る。
4. [ ] `(2) state` のスティック値、`(3) CRSF ch` が操作に追従（172〜1811、CH3=throttle最小で172付近）。
5. [ ] `(5) frame` 末尾 CRC が **OK**。
6. [ ] **ズレる場合**: `src/usb_gamepad.c` の `process_gamepad_report()` を実機バイト配置に合わせて調整・再ビルド・再書込。

> ✅ 合格条件: 全スティック/主要ボタンが期待するCRSF chに正しくマップされCRC OK。
> 記録: VID/PID、バイト配置、パーサ調整の有無を `hardware-validation.md` 記録テンプレへ。

**実施記録 (2026-07-17): ❌ 未合格 → (2026-07-18): ✅ 原因判明・ワークアラウンドで解決。**
（以下の 2026-07-17 の調査履歴は原因特定までの経緯。結論は直後の「続報 (2026-07-18)」を参照）

---
### 続報 (2026-07-18): ✅ 解決 — 原因は RP2040 のチップバグ + F310 の DATA1 開始

**まず Full Speed は無罪だった。** 対照デバイス EM01NL（Full Speed）が正常にレポートを返した
（最初の1回は沈黙したが、それは**マウス側の一時不具合**で、挿し直したら動いた）。
→ **問題は F310 固有**と確定。

**動く EM01NL と動かない F310 を debug2 で比較**して差分を2つに絞った:
| | EM01NL(動く) | F310(動かない) |
|---|---|---|
| 割り込みIN maxpacket | 8バイト | **32バイト** |
| 割り込みOUT EP | なし | **あり(EP0x02)** |
| 転送 | `Queue EP82 → on EP82 with 4 bytes: OK` ✅ | `Queue EP81 →（complete来ず）` ❌ |

**真因（TinyUSB issue #2776）**: RP2040 の自動ポーリング型EPハードウェアは**データシーケンス
エラーから回復できないチップバグ**を持つ。F310 は**最初の Interrupt IN 転送を DATA0 ではなく
DATA1 PID で開始する**（F310ファーム側の癖）。RP2040 は初期PIDを DATA0 決め打ちで待つ
（`ep->next_pid = (num == 0 ? 1u : 0u)`）ため、シーケンスエラー→**EP0x81 が無限ループでフリーズ**。
→ maxpacket も OUT EP も**無関係**だった（両方とも濡れ衣）。

**ワークアラウンド（実機で成功）**: F310 の EP0x81 を開くとき初期PIDを DATA1 にする。
→ `# HID first report: len=20`、以降 8バイトレポートが連続受信（1010回/30秒）。
**軸4本すべてが CRSF ch(172〜1811)に正しく追従することを実機確認**。昨日解読した軸配置
（report[0..3]）が正しいと裏取り完了。

⚠️ **改変は SDK 内の TinyUSB を直接いじった一時状態（git管理外・要恒久化）**:
- ファイル: `$PICO_SDK_PATH/lib/tinyusb/src/portable/raspberrypi/rp2040/hcd_rp2040.c`
- 関数 `_hw_endpoint_init`（324行付近、`ep->next_pid = (num == 0 ? 1u : 0u);` の直後）に、
  `tuh_vid_pid_get(dev_addr,...)` で VID/PID を取り、**046D:C216 かつ ep_addr==0x81 なら
  `ep->next_pid = 1u`** にする数行を追加（`// ワークアラウンドここまで` で挟んである）。
- `host/usbh.h` が既にincludeされているので `tuh_vid_pid_get` はそのまま使える。

**残タスク（次回）→ 全て完了 (2026-07-18)**:
1. ✅ **ワークアラウンドの恒久化**: 選択肢(b)採用。`patches/hcd_rp2040_f310_data1.patch` と
   冪等な適用スクリプト `scripts/apply_sdk_patch.sh` を追加。SDK入れ直し後に1回実行する運用。
   （※スクリプトの冪等判定マーカーは実在文字列 `expresslrs_realtime_recorder Stage C`、
   `patch -N` で逆適用の誤爆も防止。初版はマーカー不一致でパッチを逆適用消去するバグがあり修正済み。）
2. ✅ **F310専用パーサ追加**: `process_f310_report()` を新設し VID/PID(046D:C216)で分岐。
   D-Pad(ハット)は `report[4]&0x0F`、フェイスボタンは byte4上位4bit、ショルダー等は byte5。
   **全14項目（軸を除く全ボタン＋D-Pad4方向）を実機 `d` スナップショットで全数検証・全正解**（下記）。
3. ✅ **`CFG_TUSB_DEBUG` を 2→0 に戻した**（実飛行時オーバーヘッド回避）。
4. ✅ **各ch追従＋CRC OK 確認済** → **Stage C 正式合格**。

**ボタン実機検証結果 (2026-07-18)**（中立: `HID raw = 80 7F 80 7F 08 00 00 FF`）:

**（以下 2026-07-17 の調査履歴。原因特定の経緯として保存）**

### 使用パッド: Logitech F310

裏面に **X(XInput) / D(DirectInput) 切替スイッチ**がある。

- **X モード (PID 046D:C21D)**: USBとしてはベンダー固有クラス（Xbox360プロトコル）で、**HIDではない**。TinyUSBにはHIDホストドライバしか積んでいないため、`# USB mounted` は出るが `# HID mounted` は絶対に来ない。**このモードでは原理的に動かない。**
- **D モード (PID 046D:C216)**: 標準HIDゲームパッド(Dual Action相当)として現れ、HIDドライバがマウントできる。**必ずDにしてから挿し直すこと**（スイッチを動かすだけでは反映されない）。

### 判明したこと（Dモード）

列挙は**完全に成功**する。Full Speed / EP 0x81 IN(32B, interval 4) + EP 0x02 OUT(32B) / Set Idle OK / レポート記述子99バイト取得OK / `# HID mounted` まで到達。
**しかし割り込みIN転送が一度も完了しない。** `hcd_edpt_xfer` は `OK` を返す（＝ハードは4ms毎にEP 0x81をポーリングしている）のに、パッドが応答しない。制御転送(EP0)は全て成功しているのでパッド自体は生きている。

### 対照実験

| デバイス | 速度 | 割り込みEP | 接続 | 結果 |
|---|---|---|---|---|
| マウス (056E:00FC) | Low Speed | IN 1本 | **無線(ドングル)** | ✅ レポート届く(218回) |
| キーボード (0566:3029) | Low Speed | IN 2本 | **有線** | ✅ レポート届く(50回) |
| **F310 (046D:C216)** | **Full Speed** | IN + **OUT** | 有線 | ❌ 沈黙 |

→ **USBホストスタックと割り込みIN転送自体は正常**。F310固有の問題。
→ 割り込みINが複数でも動くので**EP本数は無罪**。
→ 対照2つが**どちらもLow Speed**なのが弱点。速度差の分離ができていない。

### 否定済みの仮説
- **割り込みOUT EP(EP 0x02)の干渉**: `int_ep_ctrl` のビット2を直接落としてOUT側のポーリングを止めても**変化なし**。→ 無罪。
- **E15エラッタによる転送保留**: デバイスモード専用でホストビルドではマクロごと `false`。→ 無関係。
- **初期化ミス/`tuh_task()`未呼び**: 列挙が通る時点で否定。
- **電源不足（パッドの消費電力が大きくて動けない）**: **否定済み**。①**F310接続状態でVBUS実測4.96V**（USB規格下限4.75Vに対し余裕あり）＝パッドには正常な5Vが届いている。②PSUは制限1Aに対し実測30mA(Pico 20mA+パッド約10mA)で**電流制限に当たっていない**＝パッド自身が引いていない。③電力不足の典型症状は列挙失敗か切断ループだが、99バイトのレポート記述子取得まで完走し切断もしない。④**有線キーボードは数十mAを消費して正常動作**した。

### 残る容疑
**Full Speed**（対照2つが偶然どちらもLow Speedで、分離できていない）。ただしPico+TinyUSBでFSのHIDが全滅なら世界的に問題になるはずで、事前確率は低い。**次回はFull SpeedのHIDデバイス（ゲーミングマウス等）で対照実験するのが最優先。**

### 次回の手順（優先順）
1. **Full SpeedのHIDデバイスで対照実験** ← 本命の切り分け。**対照デバイスは確保済み**:
   **ELECOM EM01NL トラックボール**の2.4GHzドングル（`2.4G Receiver`, Compx **25A7:FA61**）が
   **Full Speed** であることをMac側で確認済み。これをPicoに挿すだけで決着する。
   - **レポートが届く** → Full Speedは無罪 → **F310固有**と確定 → 手順2(XInput)へ
   - **沈黙する** → **Full Speed全般が黒** → RP2040ホストドライバ側の問題と確定 → 追及の的が変わる
   - ※ Mac側での事前スクリーニングは `ioreg -p IOUSB -w0 -l | grep -E '"USB Product Name"|"Device Speed"'`
     （`Device Speed` は 0=Low, 1=Full, 2=High, 3=Super。`system_profiler SPUSBDataType` は空を返すので使えない）
2. **XInputドライバを入れる**（F310本来のXモードで使う。Pico+TinyUSBでXboxパッドを扱う実装は前例が多い）
3. **別のゲームパッドを試す**（動けば前進、動かなければFS全般が黒と確定できて情報量が大きい）

### 解読済み: F310(Dモード)のHIDレポート配置 ※レポートさえ届けば即対応可能
レポート記述子(99バイト)を解読した結果、**8バイト**レポートで以下の配置。

| バイト | 内容 |
|---|---|
| 0 | X = 左スティックX (0-255) |
| 1 | Y = 左スティックY |
| 2 | Z = 右スティックX |
| 3 | Rz = 右スティックY |
| 4 | **下位4bit = D-Pad(ハット, 0-7, 8=中立)**、上位4bit = ボタン1-4 |
| 5 | ボタン5-12 |
| 6-7 | ベンダー固有16bit |

→ 現行 `process_gamepad_report()` の**軸割り当て `report[0..3]` はそのままで正解**。
→ **ボタンのみ要修正**: `buttons = report[4]` だとハット値が混入する。正しくは
  `buttons = ((report[4] >> 4) | (report[5] << 4)) & 0x0FFF` 、ハットは `report[4] & 0x0F`。

### 調査の再現方法
- `include/tusb_config.h` の `CFG_TUSB_DEBUG` を **2** にすると列挙・転送が全部ログに出る。
  CMakeが `-DCFG_TUSB_DEBUG=0` を注入するので `#ifndef` ガードでは効かず、**`#undef` してから定義**すること。
- `src/usb_gamepad.c` の mount/umount/first-report ログは常設。`# HID first report: len=N` が
  出れば受信できている（マウント毎にリセットされる）。
- screenはコピペしづらいので、pyserialでファイルに落とすと速い。**この変換器では115200を指定**すること
  （8倍ずれの既知問題。Stage B参照）。TinyUSBのログはNULが大量に混じるので `replace(b'\x00', b'')` してから読む。

## Stage D — TX疎通（CRSF反転切り分け・オシロ活用）

目的: Nano TX V2 経由で機体までRCを通す。反転/半二重/ボーレートを確定。**プロペラ無し**。

1. [ ] **オシロでGP0を観測**: 送信バーストが出ているか、ボーレート≒921.6kbps、アイドルレベル（反転ON→アイドルLow）を確認。
2. [ ] 機体(Pavo Pico)受信機を対象TXにバインド済みにする。
3. [ ] SIMPLEで BetaflightのReceiverタブを開き、スティック/スイッチが追従するか確認。
4. [ ] **通らない場合の切り分け**（§5）:
   - オシロで極性が想定と逆なら `src/main.c` の `#define CRSF_INVERT_SIGNAL 0` に変更・再ビルド・再書込。
   - Nano TX側のシリアルプロトコル=CRSF設定も確認。
5. [ ] Arm(CH7=Aボタン)でモーターArm、放してDisarm（ペラ無し）。
6. [ ] **反転ON/OFFどちらで疎通したかを記録**し、CLAUDE.md/README/コードを実機結果に合わせる。

> ✅ 合格条件: Receiverタブで全ch追従、Arm/Disarm動作。反転極性を実機で確定。

## Stage E — 記録→再生・フェイルセーフ

目的: 記録フロー全体と切断時の安全動作を実機で確認。

1. [ ] RECORD(赤LED)で数十秒操作 → `# recording started`。
2. [ ] 短押しで抜ける → `# recording stopped, flushed N samples`（N>0）。
3. [ ] PLAYBACK(緑LED) → `# playback ready: N samples`。
4. [ ] **長押し**で再生開始 → Receiverタブで記録操作が再現。末尾で `# playback finished`。
5. [ ] 電源再投入後もPLAYBACKでNが残る（フラッシュ永続）。
6. [ ] フェイルセーフ: SIMPLEでArm状態にし**パッドを引き抜く** → 内蔵LED点滅・スロットル最小・Arm解除。再接続で復帰。

> ✅ 合格条件: 記録→再生の一巡再現、切断で安全値、再接続で復帰。

## Stage F — ユニバーサル基盤へ移設

目的: 検証済み回路を `docs/perfboard-layout.html` に従いハンダ実装し、短縮版で再検証。
